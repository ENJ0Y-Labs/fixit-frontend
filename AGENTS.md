# AGENTS.md

## FixIt Frontend Team Guide

This file is the shared engineering contract for the FixIt frontend team.

The repository contains three frontend applications:

- `fixit-customer/` - customer-facing marketplace
- `fixit-provider/` - service-provider application
- `fixit-admin/` - administration application

The frontend team owns the user interface and client-side application behavior. Backend services own server-side business rules, authentication enforcement, authorization, persistence, payments, and data integrity.

Do not edit this file casually. Shared rules belong here. App-specific rules should live in an `AGENTS.md` inside the relevant application directory.

---

## 1. Product

FixIt is a two-sided home-services marketplace connecting customers with trusted local service providers in Nigeria.

The platform has three frontend surfaces:

### Customer
Customers can:
- Discover services and providers
- Search and filter providers
- Post jobs
- Receive and review bids
- Manage active and completed jobs
- Communicate with providers
- View and manage payments
- Review providers
- Manage their account

### Provider
Providers can:
- Create and manage their provider profile
- Manage services and service categories
- Set availability
- Discover available jobs
- Submit bids or responses
- Manage accepted jobs
- Update job progress
- Communicate with customers
- View earnings and payment information
- View customer reviews

### Admin
Admins can:
- Monitor the platform
- Manage customers
- Manage providers
- Review and verify providers
- Manage jobs
- Handle support and disputes
- Manage service categories
- View reports and analytics
- Manage administrative settings

Frontend visibility is not authorization. Hiding an admin button does not secure an admin action. The backend must enforce permissions.

---

## 2. Frontend Ownership

Frontend developers own:

- React components and JSX
- CSS and responsive layouts
- Client-side state
- Client-side validation
- Navigation and page composition
- Loading, empty, success, and error states
- Accessibility
- API integration
- Frontend tests
- UI performance
- Frontend environment configuration

Frontend developers do not own:

- Database schema or migrations
- Server-side authorization
- Password hashing
- Session/JWT security implementation
- Payment processing
- Server-side validation
- Business-rule enforcement
- Secrets
- Data integrity guarantees

If a feature requires backend behavior, document the required API contract instead of inventing a frontend-only workaround.

## 4. Technology

The current frontend direction is:

- React
- Vite
- JavaScript
- CSS
- ESLint
- Font Awesome where appropriate

Do not introduce a new framework, state-management library, CSS framework, or UI library without a clear reason.

The customer application currently uses React hooks and client-side page switching rather than React Router. Preserve the existing architecture unless there is a documented reason to change it.

Do not rewrite working architecture merely because another approach is fashionable. Humans already have enough unnecessary migrations.

## 6. Design System

The FixIt interface should feel like one product even though it has three applications.

Use a shared visual language:

- Clean
- Minimal
- Professional
- Compact
- Card-based
- Light backgrounds
- Strong black primary actions
- Subtle borders
- Subtle shadows
- Rounded corners
- Clear typography
- Consistent spacing

```css

--surface: #ffffff;
--black: #171717;
--text: #222222;
--muted: #6f6f6f;
```

## 7. Component Rules

Every component should have one clear responsibility.

Prefer:

```
Page
  -> Section
      -> Feature component
          -> Small reusable component
```

Avoid giant components that contain:
- API calls
- complex state
- markup for several unrelated sections
- validation
- formatting
- navigation
- styling logic

Keep business logic out of presentational components where practical.

Use descriptive component names.

Examples:

- `ProviderCard.jsx`
- `JobCard.jsx`
- `JobStatusBadge.jsx`
- `AdminSidebar.jsx`
- `VerificationTable.jsx`

Do not create abstractions merely because two components happen to have similar markup once.

---

## 8. State Management

Use React state and hooks for local application state unless the project has a demonstrated need for something more complex.

Rules:

- Keep state as close as practical to where it is used.
- Do not duplicate the same source of truth in several components.
- Derive values instead of storing unnecessary duplicate state.
- Do not mutate state directly.
- Keep temporary UI state separate from server data.
- Clearly distinguish mock data from real API data.

Avoid Redux, Zustand, or another global state library unless the application has a real requirement for it.

---

## 9. API Integration

The frontend must consume the backend contract. It must not invent undocumented endpoints.

Prefer a dedicated API layer such as:

```
src/
└── api/
    ├── auth.js
    ├── jobs.js
    ├── providers.js
    ├── users.js
    └── admin.js
```

The exact structure may vary by application.

API functions should handle:
- Request construction
- Authentication credentials where required
- Response parsing
- HTTP error handling

Components should not contain repeated raw `fetch()` logic everywhere.

When the backend contract is unknown, record the required:
- Method
- Endpoint
- Request body
- Query parameters
- Expected response
- Error responses
- Authentication requirements

Do not silently guess.

---

## 10. Authentication and Authorization

Authentication state should have clear UI states:

- Loading
- Unauthenticated
- Authenticated
- Session expired
- Authentication error

Frontend authentication state is not a security boundary.

The backend must enforce:
- Authentication
- User identity
- Role permissions
- Resource ownership
- Admin permissions
- Provider permissions

Never place secrets in frontend code.

Any Vite environment variable exposed to client code should be treated as public.

Do not put:
- Database passwords
- Private API keys
- Payment secrets
- JWT signing secrets
- Admin secrets

in frontend environment variables.

---

## 11. Forms

Forms must provide:

- Clear labels
- Useful validation messages
- Required-field indication
- Loading state during submission
- Success feedback
- Error feedback
- Disabled submit state when appropriate

Do not rely only on HTML validation when the user needs a meaningful product-specific message.

Client-side validation improves UX. It does not replace server-side validation.

---

## 12. Loading, Empty, and Error States

Every API-driven screen should account for:

1. Loading
2. Success with data
3. Success with no data
4. Request failure
5. Unauthorized/forbidden response
6. Session expiration where relevant

Do not leave users staring at a blank screen while a request happens.

Avoid fake loading states that hide actual failures.

---

## 13. Jobs and Statuses

Use consistent terminology across all applications.

Known customer-facing job statuses include:

- AWAITING BIDS
- IN PROGRESS
- COMPLETED
- CANCELLED

Provider and admin interfaces may expose additional backend statuses if the API defines them.

Do not invent new status values in the frontend.

Status labels should be mapped from backend values in one place where practical.

---

## 14. Nigerian Product Context

FixIt is designed for the Nigerian market.

Use:

- Naira: `₦`
- Nigerian phone-number conventions
- Nigerian locations where mock data is required
- `en-NG` formatting where appropriate

Do not hard-code unrealistic foreign examples when Nigerian examples are available.

Mock locations may include cities and areas such as Port Harcourt, Lagos, Abuja, Lekki, Ikeja, GRA, etc., when appropriate to the screen.

Do not imply that mock data is real platform data.

The customer application currently includes areas such as:

- Home
- My Jobs
- Post a Job
- Job Details
- Payment
- Review
- Messages
- Account
- Navigation
- Footer

Existing customer features include provider discovery, search/filtering, job posting, job management, messaging, payment UI, reviews, profile management, and responsive layouts.

## 16. Provider UI Rules

The provider application should be designed around completing service jobs efficiently.

Provider screens should make it easy to understand:

- What jobs are available
- Which jobs require action
- Which jobs are accepted
- What the customer expects
- Where the job is located
- What amount is involved
- What the current job status is
- What communication is pending

Provider actions must clearly distinguish:
- View
- Bid/respond
- Accept
- Start
- Update progress
- Complete
- Message

Do not expose actions that the backend has not authorized.

---

## 17. Admin UI Rules

The admin application is an operational interface, not another customer dashboard with a darker sidebar.

Prioritize:

- Data density where useful
- Clear tables
- Search
- Filtering
- Sorting
- Pagination
- Status indicators
- Confirmation for destructive actions
- Audit-friendly information
- Clear user/provider/job relationships

Admin actions that affect users, providers, jobs, verification, or disputes should make consequences clear.

Destructive actions should not be one accidental click away.

Frontend permission checks improve the interface. Backend authorization remains mandatory.

---

## 18. Messaging

Messaging UI should support:

- Conversation list
- Search
- Active conversation
- Message history
- Composer
- Sending state
- Error state
- Online/offline indication when supplied by the API
- Job context where relevant

Do not fabricate message delivery guarantees.

If real-time messaging is not implemented, do not label a polling or local-state prototype as real-time.

---

## 19. Payments

Payment screens are frontend interfaces unless a documented payment integration exists.

Do not:
- Store card secrets
- Handle payment credentials manually
- Pretend a local payment simulation is a completed transaction
- Invent payment APIs

The backend/payment provider must own actual transaction processing and verification.

The frontend should display payment state received from trusted backend responses.

---

## 20. File and Image Uploads

For provider documents, job photos, profile photos, and other uploads:

- Validate type and size on the client for UX.
- Show upload progress where available.
- Show failure states.
- Preview images when appropriate.
- Do not assume client-side validation is security.
- Do not expose storage secrets.
- Follow the backend upload contract.

Never trust a file simply because the browser accepted it.

---

## 21. Accessibility

Build accessible interfaces from the beginning.

Requirements include:

- Semantic HTML
- Labels for form controls
- Keyboard-accessible controls
- Visible focus states
- Useful button text
- Meaningful alt text
- Adequate contrast
- Logical heading structure
- Accessible error messages

Do not use a `<div>` as a button when a `<button>` exists.

Icons should not replace necessary text unless their meaning is already clear and accessible.

---

## 22. Responsive Design

The frontend must work across:

- 320px
- 375px
- 430px
- 768px
- 1024px
- 1280px
- 1440px

Use responsive layouts rather than designing only for one screen width.

The existing customer application uses breakpoints around:

- 1100px
- 1050px
- 760px
- 560px
- 520px
- 440px

These are implementation details, not laws of nature. Adjust them when the actual layout requires it.

Test:
- Small phones
- Large phones
- Tablets
- Laptops
- Large desktop screens

Do not fix mobile by simply shrinking desktop UI until it becomes unreadable.

---

## 23. CSS Rules

Prefer:

- Existing variables/tokens
- Component-level class names
- Reusable layout rules
- Responsive media queries
- Consistent spacing

Avoid:
- Excessive !important
- Inline styles for normal styling
- Deep selector chains
- Duplicate global rules
- Random magic numbers
- Copy-pasted responsive overrides

If an existing CSS file already contains duplicate rules, consolidate them incrementally when touching that area.

Do not create a second CSS architecture beside the first one.

---

## 24. Icons

Font Awesome is currently used in the customer application.

Use the existing icon system consistently.

Do not mix several icon libraries for no reason.

Icons should support the interface, not turn every button into a mysterious little symbol puzzle.

---

## 25. Mock Data

Mock data is acceptable while backend integration is incomplete.

Rules:

- Keep mock data clearly identifiable.
- Put larger mock datasets in dedicated files.
- Do not scatter large arrays throughout JSX.
- Use realistic Nigerian examples.
- Do not mix mock records and API records without a clear strategy.
- Remove temporary mocks when the real API replaces them.

A mock should model the expected API shape where possible.

---

## 26. Performance

Avoid unnecessary work.

Use:
- Lazy loading for appropriate pages
- Stable list keys
- Pagination for large datasets
- Debounced search when appropriate
- Optimized images
- Derived state instead of duplicated state

Do not optimize imaginary problems.

Measure or identify the actual bottleneck before introducing complicated caching or memoization.

---

## 27. Error Handling

Never silently swallow important errors.

Bad:

```js
try {
  await saveJob();
} catch {
}
```

Better:

- Log useful development information where appropriate.
- Show a user-friendly message.
- Preserve the user's entered data when possible.
- Allow retry where appropriate.

Do not display raw backend stack traces to users.

---

## 28. Git Rules

Use focused commits.

Good examples:

```
feat(customer): add job posting form
feat(provider): add provider dashboard
feat(admin): add provider verification table
fix(customer): correct mobile navigation
fix(provider): handle failed bid submission
fix(admin): show forbidden state
```

Avoid giant commits such as:

```
update stuff
fix everything
frontend work
final final
```

Commit messages should explain the change.

Do not modify unrelated files while implementing a feature.

Do not overwrite another developer's work without understanding why it exists.

## 29. Pull Requests

A frontend PR should include:

- What changed
- Which application changed
- Screens/pages affected
- API changes required, if any
- Testing performed
- Responsive testing performed
- Known limitations

Keep PRs focused.

If a feature requires backend work, state the backend contract dependency explicitly.

---

## 30. Testing

Before considering a feature complete:

- Run ESLint.
- Run the application's build.
- Test the main user flow.
- Test validation failures.
- Test loading state.
- Test empty state.
- Test API error state when applicable.
- Test unauthorized/forbidden behavior when applicable.
- Test mobile and desktop layouts.

For important reusable logic, add automated tests where the project setup supports them.

Do not claim a feature works because the happy path worked once.

---

## 31. Definition of Done

A frontend feature is done when:

- The UI matches the intended product behavior.
- The component structure is understandable.
- Responsive behavior works.
- Loading/empty/error states exist where required.
- Accessibility basics are covered.
- Client validation exists where useful.
- API integration follows the documented contract.
- No secrets are exposed.
- ESLint passes.
- The production build passes.
- No unrelated files were changed.
- Mock data is clearly separated from real data.
- The feature has been manually tested at relevant screen sizes.

---

## 32. Feature Development Workflow

Follow this order:

1. Understand the product requirement.
2. Identify which application owns the feature.
3. Inspect the existing component and CSS structure.
4. Identify whether backend/API support exists.
5. Define the UI states.
6. Build the smallest correct component structure.
7. Add styling using existing design tokens.
8. Add responsive behavior.
9. Add API integration if available.
10. Handle loading, empty, error, and permission states.
11. Test the main flow.
12. Run lint/build.
13. Review the diff for unrelated changes.
14. Commit the focused change.

Do not start by rewriting the application.

---

## 33. Backend Collaboration Contract

When the frontend needs backend support, provide the backend team with a concrete contract.

Example:

```
GET /api/jobs

Query:
  search
  category
  status
  page
  limit

Response:
{
  "items": [],
  "page": 1,
  "limit": 20,
  "total": 0
}
```

The exact contract must come from the backend team or approved API documentation.

Frontend developers may propose an API contract, but must not silently assume it is implemented.

---

## 34. Security Rules

Never:

- Put secrets in frontend source code.
- Trust frontend role checks as authorization.
- Trust client-side validation as security.
- Store sensitive credentials in localStorage without an explicit security decision.
- Expose internal backend errors.
- Build security-critical behavior entirely in JavaScript.

Treat all browser input as untrusted.

---

## 35. Product Principles

Build for clarity before cleverness.

Prefer:
- Simple flows
- Obvious actions
- Consistent terminology
- Predictable navigation
- Useful feedback
- Small reusable components
- Explicit states

Avoid:
- Feature creep
- Premature abstraction
- Hidden state
- Duplicate sources of truth
- Giant components
- Unnecessary dependencies
- UI that looks impressive but is difficult to use

The goal is not to make the code look advanced.

The goal is to make the frontend reliable, understandable, and ready for real users.

---

## 36. Final Rule

Build the frontend around the approved FixIt product requirements and documented backend contracts.

Do not invent backend behavior.

Do not use frontend code to fake security.

Do not rewrite working architecture without a reason.

Do not sacrifice usability for visual novelty.

Keep the three applications consistent as one FixIt product while allowing each application to solve its own users' problems.

Build cleanly. Test the actual flows. Keep the scope under control.
